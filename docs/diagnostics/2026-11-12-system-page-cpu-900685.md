# System page "CPU maxed out" on the OVH host — diagnosis (obj 900685)

Reported in Operator's Operation Kit feedback walkthrough (recorded 2026-11-12, chapter
"10:22 System & Email Setup"). Measurements below were taken on 2026-11-12 between
14:43 and 14:50 UTC from a worker session on the same host. `/proc/stat`, `/proc/loadavg`
and `/proc/pressure/cpu` inside the session are host-wide, the same counters the server
reads.

## Short answer

- **The reading is accurate.** The page shows real host-wide CPU: all 32 threads of the
  AMD EPYC 7313, every container, every session. It does not measure only the Command
  Center container or the Node server.
- **The load comes from worker sessions, not the server.** At the peak, about 75% of all
  CPU time was `nice` time. Every worker session renices itself to 15
  (`session-tmux.ts`). Un-niced user time, which includes the Node server and state
  poller, stayed at 0–2%. Kernel (`sys`) time was 15–24%.
- **What those sessions were doing:** 16 worker cards were `working` at once. Most were
  filed from the same walkthrough (900666–900684), all on operationkit, each
  running `npm ci`, `tsc`, `vitest` and `vite build` in its own worktree. Several of those
  runs at the same moment push the box to 90–100%.
- **Why it looked worse than it is:** the page measured one 500 ms window per poll. On
  this box that number swings hard (17%→59% in one idle-ish minute, 58%→96%→63% in a busy
  one). Nothing on the page said what was using the CPU, so a burst from sessions looked
  like the server being maxed out. Averaged over the 6 days since boot, the box is
  **1.26% busy**.
- **Is it harmful?** Mostly no. Sessions run at nice 15, so the control plane stays
  responsive. CPU pressure (`some`) reached avg10 ≈ 12.5%, `full` stayed 0. The real costs
  are slower worker builds and tests while many cards run at once, and the high share of
  kernel time, which is worth a look on the host.

## Evidence

### 1. The metric is host-wide and computed correctly

`GET /api/admin/system` (`app/server/src/routes/admin-ops.ts`) read `os.cpus()`, which on
Linux is `/proc/stat`. It took two snapshots 500 ms apart and reported
`1 − Δidle/Δtotal`. libuv's `os.cpus()` exposes `user,nice,sys,idle,irq` (checked in the
session: `times keys user,nice,sys,idle,irq cores 32`). iowait/steal are left out of the
total, and iowait was 0 throughout, so nothing inflates the number. Since Aug 2026 the
same math has been in this repo and in the public OperationKit repo that OVH runs
(8dda286b, #82).

The same computation run from a session, 120 × 500 ms samples:

```
times keys user,nice,sys,idle,irq cores 32
n 120 min 16.7 p50 26.0 p95 37.9 max 59.0 load 12.23/5.60/2.38
```

### 3. Who was running

`GET /api/internal/objectives?status=working&fields=minimal` from the session (scoped to
the operationkit workspace) returned `X-Total-Count: 16`. These were 900666–900685,
mostly cards from the same walkthrough, all build/test-heavy work on this repo. This
session's own `npm ci` and `tsc` (nice 10–15) ran during part of the window too and are
counted in the `nice` share.

### Limit of this diagnosis

The worker sandbox has its own PID namespace, so it cannot list host processes by PID.
Attribution is by CPU class: `nice` means worker sessions, user time at nice 0 means the
server and other services, and `sys` is kernel. Attribution is also by what was running
on the board. A per-PID view (`top`, `pidstat`) needs host access. The card says no host
changes, and reading `top` there would only confirm which session's build was hot.

## Recommended fixes

1. **Make the page honest (this PR).** Replace the single 500 ms sample with an
   in-process sampler (one `os.cpus()` read every 2 s, only while someone is polling the
   page). Show a ~10 s average, the 1-minute average and peak, and a
   **Sessions / Kernel / Server-other** split, so a session burst no longer reads as
   "server maxed".
2. **Cap client vitest workers (this PR).** `app/client/vitest.config.ts` had no cap.
   Vitest sizes its pool to the CPU count, so each client test run on this host starts
   about 31 workers. Server tests are already capped at 2 (2026-08-16 OOM incident). This
   PR applies the same cap to the client.
3. **Limit concurrent build-heavy workers per repo (follow-up, not in this PR).** A
   walkthrough that files 15+ cards on one repo starts 15+ simultaneous
   `npm ci`/`tsc`/`vite build` runs. Options: a per-project concurrency ceiling in the
   queue drain, or a shared `node_modules` cache per worktree base so every card does not
   run `npm ci`.
4. **Look at the kernel share on the host (needs Operator's OK).** `sys` at 15–24% of the
   whole box during bursts is high. Likely sources are process churn: jail/container
   spawn, `npm ci` extracting thousands of files, and per-session `tmux has-session`
   polling loops. Confirm with `pidstat -u 5` or `perf top` on the host before changing
   anything.
5. **Optional:** a `cpu.max` cgroup limit on the session jails would cap the total that
   sessions can take. This changes the host or compose config, so it needs Operator's ask.

No production or host changes were made. Nothing was deployed.
